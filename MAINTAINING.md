# Maintaining — SSV Silver Gull Settlements

Everything you need to add a town, change a floorplan, or ship a release.

---

## 1. The architecture, in one rule

| file | rule |
|---|---|
| `scripts/settle-render.js` | **Pure.** Styles, all rendering, and all floorplan geometry. `grep -nE '\b(game\|ui\|Hooks\|canvas)\.' scripts/settle-render.js` must return **nothing**. Loaded as a classic script so `globalThis.SSVSET` exists before the esmodule runs. |
| `scripts/settlements.js` | **Foundry only.** Settings, hooks, keybinding, socket, scene building, NPC tokens, the wander engine, the shop bridge. |

That split is what makes `../preview.html` possible: it loads the *real* renderer in a bare
browser against a fake `ctx`. Iterate there, not in Foundry.

```bash
python3 vtt/settlements/tools/serve.py     # http://localhost:8794/preview.html
```

The preview has two tabs. **Hub** is the settlement view, with a GM/player switch and a
time-of-day selector. **Floorplan** draws the derived walls, doors, lights, spawn, exit and
NPC posts *over* the map art — this is the check that the geometry actually matches the
picture, whether it was detected off finished art or derived from an ASCII plan.

---

## 2. Content vs. state — the rule that bites

`data/settlements.json` is **content**. It is regenerated by the build script and shipped
with every release, so **it is overwritten on update**. Anything live — what the party has
discovered, what is locked, who is inside which building, the time of day, which scene
belongs to which location — lives in the world setting `state` and is merged over the
content at render time (`annotate()` in the renderer, `getState()` in the wiring).

Never write live state into `settlement_parts.py`.

---

## 3. Maps and geometry — how an interior gets made

**The art is authoritative and the geometry is read off it.** A battlemap is generated as
finished art with nothing drawn onto it; the walls, doors and lights are then found in the
image and created as Foundry `Wall` and `AmbientLight` documents on top. That ordering
matters — see the note at the end of this section for why the reverse does not work.

### The pipeline

```bash
# 1. generate the art (gpt-image-1, 1536x1024, nothing drawn on it)
python3 tools/gen_freeform_maps.py frostwatch-the-trade-post

# 2. find the walls and lights in it
python3 tools/analyze_map.py ../art-src/interiors/frostwatch-the-trade-post.png --grid 64

# 3. review <stem>-walls.png, then paste <stem>-geometry.json into settlement_parts.py,
#    adding by hand: doors, spawns, exits, posts, waypoints
python3 tools/build_settlements.py
node tools/check_geometry.js
```

`analyze_map.py` keys on linework: pixels markedly darker than their surroundings, gathered
into long straight runs. Absolute darkness is useless — a night interior is dark everywhere
and a plain threshold floods the map. Runs shorter than about a square and a half are
dropped, because furniture is outlined in the same ink as walls.

**The detector is a proposal, not the answer.** It misses walls and it invents a few along
furniture edges. Two things fix that: correcting the JSON against the review overlay, and —
better — tidying up in Foundry afterwards with its own wall tools, which are far better than
anything worth building here. Hand edits survive everything except a scene **Rebuild**.

Doors, spawn points, exit zones and NPC posts are **always** marked by hand. Nothing
reliably distinguishes a drawn door from a drawn wall. They go in the same geometry block:

```jsonc
"geometry": {
  "size": [1536, 1024],
  "walls":  [[x0,y0,x1,y1], ...],      // detected
  "doors":  [[x0,y0,x1,y1], ...],      // marked by hand
  "lights": [{"x":.., "y":.., "dim":170, "bright":70, "color":"#ffb066"}],
  "spawns": [{"x":.., "y":..}],
  "exits":  [{"x":.., "y":.., "w":.., "h":..}],
  "posts":  {"1": {"x":.., "y":..}},
  "waypoints": [{"tag":"a", "x":.., "y":..}]
}
```

All coordinates are **image pixels**, deliberately not snapped to a grid: illustrated maps
never line up with one, and forcing them to would put the collision off the art.

`gridSize` still matters — it is the Foundry grid, and it should divide the image cleanly.
A 1536x1024 map at `gridSize: 64` is 24x16 squares. The build script warns when it does not
divide evenly.

### Keep the spawn clear of the exit zone

Placing a token fires `updateToken`; a spawn sitting on the doorway would bounce the player
straight back to the hub. There is a two-second grace period in `onTokenMoved` as a
backstop, but do not lean on it. Both the build script and `check_geometry.js` fail on a
spawn inside an exit rect.

### Placeholder maps and the ASCII floorplan

An interior can instead carry an authored ASCII `plan`, in which case `tools/gen_maps.py`
draws a clean illustrated map straight from that grid via `mapart.py`, and `deriveGeometry`
derives the walls from the cell edges. This is the fallback so the module is never missing a
battlemap; the eight interiors that have not been through the art pipeline yet use it.

```
#  solid wall     =  counter    '  window     +  door    /  locked door
.  deck   :  tile   ;  planks   "  carpet   *  grating   ,  street   ~  rough
L  bright light    l  dim light
S  party spawn     X  exit zone    1-9 NPC post    a-z wander waypoint
```

A second, optional `props` grid of the same dimensions adds furniture — `T` table, `c` chair,
`B` bed, `K` crate, `b` barrel, `S` shelving, `D` desk, `W` workbench, `M` machinery,
`O` stove, `E` long table, `u` booth, `g` glassware, `p` planter. Props are **purely
decorative** and never affect movement; anything that should block goes in the `plan` as `=`.

Rules the build script enforces on authored plans: rows all the same length, a solid outer
ring apart from doors, and every exit and waypoint reachable from the spawn.

### Why the pipeline runs this way round

The obvious approach — author the floorplan, then have the model paint art to match — was
tried and abandoned. gpt-image-1 paints beautifully but will not respect a layout: across
several attempts it thickened counters, shifted them half a square, and invented rooms on
open floor. The `mask` parameter does **not** clamp it either; with `input_fidelity: high`
the whole frame is regenerated and the mask is only a hint. Compositing the passes locally
fixed alignment but left phantom furniture the model had painted where the floorplan said
open floor.

Reading the geometry off finished art has none of those failure modes, because the art is
never asked to match anything.

## 4. Other artwork

### One image per settlement — do not generate a second one for night

There is exactly **one** generated vista per settlement, the daylight one. Dawn, dusk and
night are graded from it by `tools/relight.py`.

This is not a shortcut. Generating night separately produced a *different building layout* —
the model does not reproduce a scene — so hotspots authored against the day image landed on
empty snow after dark. Grading the same picture cannot drift, because it is the same picture.

A flat darken reads as dimmed daylight rather than night, so each settlement carries a short
`lamps` list: normalised points marked by eye on the day image (windows, pad floodlights),
each with a radius, power and colour. `relight.py` paints those back in as warm pools with a
bloom. Tune the numbers there — they are content, not code.

```bash
python3 tools/gen_art.py cities      # the daylight image only
python3 tools/relight.py force       # dawn / dusk / night from it
```

| what | where | generated by |
|---|---|---|
| Settlement vista (daylight only) | `assets/cities/` | `tools/gen_art.py cities` |
| Dawn / dusk / night variants | `assets/cities/` | `tools/relight.py` |
| NPC portraits | `assets/portraits/` | `tools/gen_art.py portraits` |
| Interior battlemaps | `assets/interiors/` | `tools/gen_freeform_maps.py` |
| Placeholder battlemaps | `assets/interiors/` | `tools/gen_maps.py` |

All generation uses `gpt-image-1` with the key from the repo-root `.env`, and is idempotent
— only missing files are made unless you pass `force`. Full-resolution PNGs are kept in
`../art-src/`; the module gets downscaled WebP.

### Placing hotspots

`hotspot: {x, y}` is normalised 0-1 against the settlement artwork. Open the day image at
full size, read off the centre of each building, divide by the image dimensions.

The hub deliberately **letterboxes** the artwork rather than cropping it (`object-fit` is
not `cover`): the image sizes the frame and the frame shrink-wraps the image, so a hotspot
authored at 0.49/0.59 is on the same building at every window shape. If you ever switch to
`cover`, every hotspot drifts.

## 5. Scenes

`buildScene()` creates a scene named `"<Settlement> — <Location>"` carrying a flag block
(`spawns`, `exits`, `posts`, `waypoints`, `passable`, `gridSize`) that the wander engine and
the doorway check read at runtime.

**Rebuild is destructive but targeted.** It deletes and re-derives every wall, every light
and every token flagged `npcKey`. Player tokens and anything you added by hand survive. The
GM cog warns before doing it.

Scene ids are remembered in `state.sceneKeys`, with a fall back to lookup by name — so
renaming a scene in Foundry is survivable, but renaming a *location* in the content is not:
that orphans the old scene and builds a new one.

## 6. Permissions and the socket

Same discipline as the shop module. **Players never write settings.** Every mutation is
`emit({toGM: true, …})`; the *active* GM (`isActiveGM()`) validates and commits. If a second
GM is connected, only one acts — otherwise every transaction would run twice.

Player clients get told what happened over the socket (`view`, `hub`, `refresh`, `bubble`).

## 7. The shop bridge

The NPC card's **Browse wares** button calls
`game.modules.get("ssv-silver-gull-shop").api.openShop(shopId)`.

For this to work, the shop's `shopId` must match. Seeded shop ids are deterministic —
`shop-<locationId>-<shopType>` — so `shop-vorrn-7-cantina` is the cantina at Vorrn-7. Shops
are seeded from `vtt/shop/tools/catalogue_parts.py`; if you add a shopkeeper you must add
the matching shop type to that location's `seed` list and rebuild the catalogue.

Arriving in a settlement calls the shop's `setLocation(city.shopLocationId)` so region and
scarcity pricing are right, and so the shop's own "are the crew docked here" guard passes.

**Missing shops heal themselves.** The shop module seeds worlds from its own catalogue and
deliberately *skips* a world that already has shops — so a world seeded before a shopkeeper
was added never gets that shop, and clicking the keeper produced "That shop is gone." Every
shopkeeper therefore carries a `shop` spec (`type`, `locationId`, `wealth`, `size`, `name`)
and `ensureShopsFor()` mints anything missing when someone enters the location. Add a
shopkeeper and you must add that spec, or the console warns and the keeper stays mute.

**Lockdown.** Shop v0.1.3 added a world setting *Players may browse shops freely*, off by
default: with it off, `I` and the shop toolbar button do nothing for players, and a shop can
only be opened by clicking its shopkeeper. The GM is never gated.

## 8. Gotchas

- **Escape** is handled by a capture-phase listener that bails out if a Foundry dialog has
  focus, then closes the NPC card, then the hub.
- **Token clicks** are intercepted by monkey-patching `CONFIG.Token.objectClass.prototype._onClickLeft`
  once, in `ready`. A GM holding **Alt** gets the normal select behaviour so tokens stay
  editable. No libWrapper dependency, matching the rest of the repo.
- **The side-panel rows are `div role=button`, not `<button>`.** Foundry's global button
  rules (a fixed `height`, `line-height: 1`, `white-space: nowrap`) repeatedly broke the row
  layout and pushed the tag chips out onto the card above. The row restates its own box —
  `height:auto; min-height:0; line-height; white-space` — so a host rule cannot win. If you
  add a new composite control, do the same, and test it with those rules injected.
- **Scenes are gridless by default** (`interior.gridless: false` opts back into a square
  grid). The maps are illustrated art whose architecture never lines up with a square grid,
  so drawing one over the top just fights the picture.
- **The wander engine** runs on the active GM only, pauses when a combat is running in that
  scene, when nobody is viewing it, and when the venue is shut for the current time of day.
- **NPCs move in pixels, not cells.** Each one keeps a small mind in memory (`minds`): pick
  somewhere to stand, walk there in short steps, then stay put for 6-22 seconds doing
  whatever they came over to do. Steps are tested against the wall segments, so a gridless
  scene needs no grid to keep people out of walls; walking into one ends the errand rather
  than grinding. Idle NPCs are the ones picked for chatter, since a person standing still is
  the one who talks.
- **Keybinding C.** J, P, S, I and `\` are taken by the other SSV modules.
- CSS is injected from JS under the single root class `.sgset`. Do not depend on another
  module's stylesheet; copy what you need under your own root.

## 9. Release

```bash
cd "vtt/settlements/ssv-silver-gull-settlements"
# bump "version" in module.json first
node --check scripts/settle-render.js && node --check scripts/settlements.js
node scripts/settle-render.js --selftest
grep -nE '\b(game|ui|Hooks|canvas)\.' scripts/settle-render.js      # must be empty
python3 ../tools/build_settlements.py --check
node ../tools/check_geometry.js
python3 ../tools/gen_maps.py --check

git add -A && git commit -m "vX.Y.Z — what changed"
git push origin main
rm -f module.zip && zip -qr module.zip module.json scripts data lang assets README.md
gh release create vX.Y.Z module.json module.zip --title "vX.Y.Z" --notes "..."
```

Then Foundry → Setup → Add-on Modules → **Update** with
`https://github.com/Solly240/ssv-silver-gull-settlements/releases/latest/download/module.json`,
and hard-refresh (browsers cache esmodules).
